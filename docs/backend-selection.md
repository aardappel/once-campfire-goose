# Epoll default and current Campfire comparison

Measured on 2026-10-24, with unpatched goose-http v0.5.11 and goose-compress
v0.1.4. Epoll is the default for the Linux application. Ordinary Docker and the
shared verifier do not allow the io_uring syscalls; calling `serve` there uses
the ring emulation. `serve_epoll` needs no special container policy.

There is no Goose compiler blocker to using epoll. An earlier two-sample,
16-connection comparison on October 22 had roughly tied writes and overlapping
read rates (202k/s emulated, 199k/s epoll), with limited client capacity. The
measurements below use more client capacity and include live subscribers.

## Backend comparison

One identical executable serves all three modes. Each backend has four samples:
two in epoll/emulated/native order, then two in native/emulated/epoll order.
Medians are shown below; parentheses contain the individual-sample range,
not a confidence interval. Memory is cgroup anonymous memory sampled after
room reads, not total or peak process/container memory.

| Backend | Room reads/s | Posts/s, no subscribers | Messages/s delivered to all 64 subscribers | Memory after reads |
|---|---:|---:|---:|---:|
| Epoll | 393,316 (383,055–398,460) | 6,085 (6,084–6,186) | 638 (628–735) | 22.91 MiB |
| Emulated ring | 380,441 (374,032–385,393) | 6,166 (6,106–6,276) | 652 (643–659) | 29.95 MiB |
| Native io_uring | 389,790 (383,352–394,165) | 6,186 (6,161–6,244) | 663 (647–675) | 27.26 MiB |

Epoll uses 23.5% less sampled anonymous memory than emulation and has a 3.4%
higher read median. The read ranges overlap slightly. Median server CPU cost
per room response is 9.33 microseconds for epoll, 9.78 for emulation, and 9.49
for native io_uring, including kernel CPU. Writes and fan-out do not show a
large consistent backend advantage. These results do not reproduce the native
ring's documented 12–22% plaintext advantage on this application's 21 KiB gzip
pages and fan-out. The library's memory-floor ratios do not describe the entire
Campfire process.

Every native run had four kernel io_uring descriptors. Epoll and emulation had
none. Native runs used the restricted profile generated by
`scripts/io_uring_profile.py`; its SHA-256 is in each receipt. Other runs used
Docker's default policy. The profile and ring-buffer count are not required
for the epoll deployment.

## Rust and Jai on the same machine

Three rounds rotate Goose/Rust/Jai, Rust/Jai/Goose, Jai/Goose/Rust. Goose uses
epoll. The immutable published references are the current Rust application and
Jai's `2ecd487` image; Jai main `b0952a2` contains subsequent documentation.
Their application revisions were checked before the run.

| Workload | Goose | Rust | Jai |
|---|---:|---:|---:|
| Room reads/s | 386,572 (379,116–402,620) | 19,389 (19,124–19,425) | 316,656 (315,754–328,047) |
| Posts/s, no subscribers | 6,119 (6,035–6,127) | 3,467 (3,382–3,498) | 4,337 (4,298–4,346) |
| Messages/s delivered to all 64 subscribers | 647 (637–679) | 2,288 (2,228–2,297) | 3,379 (3,294–3,449) |
| Anonymous memory after room reads | 22.55 MiB | 36.41 MiB | 21.41 MiB |
| Anonymous memory after posts | 24.70 MiB | 95.34 MiB | 83.00 MiB |

Goose leads Jai by 22.1% on these room reads and 41.1% on posts without
subscribers. Jai is 5.22 times faster at complete 64-subscriber fan-out, and
Rust is 3.54 times faster there. A general claim that Goose is faster would
misrepresent this result. Post-run memory follows equal-duration workloads
with different numbers of writes; it is not a fixed-work allocation comparison.

The broker is a concrete next profiling target. It holds one publication active
until its enrolled readers return drain credits, scans connections on each
command, and scans the global subscription list for each recipient. This is
code inspection, not an attribution from a CPU profile. Candidate work includes
batching credits, indexing subscriptions and reusing encoded prefixes. Any
change must retain bounded output, ordering, disconnect recovery and the existing
acknowledgement semantics. Backend replacement alone does not close this gap.

## Validation and limits

The final image passes setup/authentication, HTTP cache on/off, session and room
revocation, rollback, WAL recovery, concurrent acknowledged writes, and
WebSocket tests on epoll, emulation and native io_uring. The delivery fixture
includes incoming fragmented commands, two-reader fan-out, a 200 KiB fragmented
publication and disconnect cleanup. Native mode refuses unavailable support
with a nonzero exit; automatic mode selects epoll under ordinary Docker.

The unchanged shared Chromium smoke suite passes. All 27 differential rendering
cases and all 315 served asset hashes match each pinned Rust/Jai reference.
Upstream's nine WebSocket/compression/timer tests pass at both -O0 and -O2,
including lazy gather release and 1013 budget exhaustion. Its drain fixtures
pass on native io_uring and epoll: 32 MiB ordered stalled-reader delivery,
disconnected-slot reuse, fair health requests and active deadlines. The native
send-allocation failure fixture also runs and passes.

All accepted measured HTTP responses pass the unmodified shared contracts with
zero errors or invalid responses. All fan-out clients connect and confirm their
subscriptions; every paced and saturated message reaches every subscriber.
Database checks verify the exact persisted message set, rich text and FTS bodies.

| Reference comparison audit | Goose | Rust | Jai |
|---|---:|---:|---:|
| Valid timed HTTP responses | 9,515,828 | 547,515 | 7,803,001 |
| Audited HTTP writes, including warmup | 180,898 | 99,246 | 129,470 |
| Audited fan-out writes | 15,774 | 54,573 | 81,045 |

A preliminary 256-writer stress run produced 2,334 HTTP 503 responses and
49,937 validated HTTP 200 responses. The validator stopped that run; none of
its throughput figures is accepted here. The application has 64 publication
permits and can reject work at admission before committing a message. The
accepted comparison uses 32 concurrent writers for every implementation and
retains 256 readers. The 64-permit bound is unchanged. Raising it or redesigning
admission is separate work; reducing benchmark concurrency does not fix that
capacity limit. The failed sample and its metadata are retained in the results.

All runs use an AMD Ryzen 9 9950X3D, WSL Linux 6.18.54.1, Docker 29.1.3, four
physical server cores (0,2,4,6), eight separate client cores (8,10,12,14,16,18,20,22),
and a 2 GiB server limit. HTTP samples last eight seconds after two seconds of
warmup. Fan-out uses the unmodified generator's `cable` command: 64 tabs of one
fixture user, six subscriptions per tab, 20 paced messages, four posters and
eight seconds of saturated delivery followed by draining. It is not a test of
64 distinct users or unlimited subscriber capacity.

The monitor waits for three quiet five-second samples before starting. Across
149 measurement samples it found no compiler process. Intermittent desktop
activity remained: Discord in 34 samples (up to 0.779 core), ChatGPT in nine
(up to 0.700), and Chrome/dllhost in one each. No user processes were interrupted.
The host was not perfectly idle. Read servers used about 3.7 cores and the
Goose/Jai clients about 7.0–7.2; these observations do not prove unrestricted
maximum capacity. Small backend differences should not be overstated.

## Provenance and reproduction

The [machine-readable results](backend-selection-results.json) retain each
sample, validation result, image identity, environment and relevant checksum,
plus the failed 256-writer run. Accepted timing ran from 18:48:48 to 19:01:12 UTC.
The functional application image is revision `1e178a8`; the benchmark harness
is `e3e4690`. Later commits only preserve results and documentation.

- Goose image: `sha256:23e7ec908667a96af24c2816718a3434ea081cd9c4293d568e8f4d5bda655857`.
- Executable SHA-256: `1cf1d78b7f21d23a15b8258117058e12b6ef034e289a385c2f88f5499512dd5e`.
- Compiler: `d9573d8139de395cd4549b876c176c25eb878fc1`.
- HTTP: `555a723adc103a455ccc4cdf43bd4a9a96608a70` (v0.5.11), unpatched.
- Compression: `6f0c17ac4ceeca930cc7cd9c6b5d9293c8b09f50` (v0.1.4).
- Verification: `ec02debb3e44f40b8778a6a42db3c4515b2f9eaf`, unmodified.

Run from a clean experimental checkout on a Linux host with Docker and the
shared verifier's Ruby dependencies/load generator available. `$VERIFY`, `$SEED`
and `$RUNTIME` name the verifier checkout, seeded fixture and disposable Linux
storage directory. Resolve the Rust/Jai images to the digests in the results JSON.

```sh
python3 benchmark_shared.py --verification "$VERIFY" --seed "$SEED" \
  --runtime-root "$RUNTIME" --output build/epoll-comparison \
  --apps goose,rust,jai --goose-backend epoll --rounds 3 --duration 8 \
  --clients 256 --write-clients 32 --client-cores 8 --fanout-clients 64 \
  --profiles baseline --routes room_show,post_message \
  --rust-image "$RUST_DIGEST" --jai-image "$JAI_DIGEST"
```

For the backend comparison, use `--apps goose --rounds 2`, unique output
directories, and backend order epoll/emulated/uring then uring/emulated/epoll.
Only `uring` needs `--goose-seccomp build/seccomp-io-uring.json`.
`CAMPFIRE_HTTP_BACKEND=auto` probes native support and otherwise chooses epoll;
`uring` requires it, and `emulated` explicitly forces the comparison path.
HTTP/3 stays disabled. No changes were made to Goose master or to the reference
applications, and the retired send-copy patch remains absent.
